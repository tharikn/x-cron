# 09 — Device-First Document Storage

## 1. Policy

Generated documents belong on the user's device by default. The backend stores structured career data and resume configuration so the document can be regenerated. It does not keep every PDF, HTML, XLSX or DOCX export.

This is a default product policy, not a claim that the service can control files after they have been downloaded or shared.

## 2. Responsibility split

**Backend**
- Stores confirmed structured career data, resume definitions and version metadata.
- Generates export bytes or a temporary response.
- Deletes temporary artifacts after delivery/TTL.
- Does not create a permanent export archive by default.

**Client**
- Receives generated bytes.
- Saves to user-selected or app-managed device storage.
- Lists local exports and allows rename/share/delete where platform APIs permit.
- Handles storage permission errors and device cleanup.

## 3. Mobile: Ionic + Capacitor

Use Capacitor Filesystem for app-managed or user-selected file operations supported by the target OS. Verify current plugin behavior and Android/iOS permission requirements during implementation.

- Save into an app documents/cache location as appropriate.
- Use cache only for regenerable temporary files.
- Offer share/open actions through supported native plugins.
- Do not silently claim a file is saved if the platform operation fails.
- Provide a clear filename and MIME type.
- Test Android and iOS separately.

## 4. Web

- Use browser download for user-visible exports.
- Use IndexedDB only for small local drafts/metadata or offline work where justified.
- Use File System Access API only when supported and after user interaction.
- Provide a normal download fallback for browsers without that API.
- Do not assume browser storage is permanent; it may be cleared by the user or browser.

## 5. Local draft behavior

- Keep active edits in client state.
- Debounce server saves for confirmed structured profile/resume changes.
- Consider encrypted local draft persistence only if offline editing is required.
- Resolve conflicts using updatedAt/version metadata and explicit conflict handling.
- Never overwrite a newer server version silently.

## 6. Export lifecycle

1. User selects a resume version and format.
2. Client requests export.
3. Backend renders or delegates rendering.
4. Backend streams bytes/returns short-lived retrieval token.
5. Client saves to device.
6. Client confirms success to the user only after the platform save succeeds.
7. Temporary server artifacts are cleaned up.

## 7. Backup and recovery

Local files can be lost if the device is lost or reset. The product must clearly explain this trade-off. A future opt-in cloud backup may be offered separately with explicit consent, retention controls and deletion support. Do not enable it silently.

## 8. Privacy

Do not log file contents or store exports in analytics. Temporary files must be access-controlled, unguessable, short-lived and removed by scheduled cleanup plus best-effort deletion after successful delivery.
